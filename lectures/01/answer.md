- 講座に固有の質問（宿題の3レベル）へのモデルの回答（要約でよい）：
  - gemini-3.5-flash-lite は「基礎・応用・発展」という一般的な3段階を推測して答えた。内容はもっともらしいが、AIE2026 の実際の定義（基礎=講義内容の確認、実装=自分でコードを書く、発展=調査や試行。どれか1つで完了）とは異なり、「応用」という存在しないレベルを作っていた。ただし自信満々に断定はせず、LMSやSlackで確認するよう案内も添えていた。
- 用語集の正しい意味と比べて気づいたこと：
  - 用語集（glossary.json の homework-levels）にある正解は「基礎・実装・発展の3段階、どれか1つに取り組めば完了、原則採点しない」。モデルは講座固有情報を知らないので一般論で補完し、レベル名を1つ間違えた。「分からない」とは言わず、妥当そうな推測で答える挙動が確認できた。一方で「正確な定義はLMSで確認を」と促す自己制限的な振る舞いも見られ、完全なハルシネーション一辺倒ではなかった。

## 宿題

- 取り組んだレベル：発展
- やったこと：
  - `scripts/bench_day1.py` を新規作成し、3モデル（gemini-3.5-flash-lite / gemini-3.5-flash / gemini-2.5-flash-lite）× 3質問 × 3回で generate_content を呼び、応答時間（perf_counter実測）と usage_metadata のトークン数を記録した。429時は60秒待って再試行するよう実装。生データは bench_day1_results.json に保存。

  - gemini-3.5-flash の Q2-run1 で `503: This model is currently experiencing high demand` が発生。レート制限（429）ではなく需要スパイクによる一時的な失敗が実際に観測できた。
- 気づき・疑問：
  - 旧世代の 2.5-flash-lite が全質問で最速（0.8〜3.4秒）だった。3.5系は同じ質問でも4〜10秒かかり、用途によっては旧モデルの方が向く場面がありそう。最新=最速ではないことを実感した。
  - 応答時間は出力トークン数より質問の複雑さとモデル世代に左右される印象。Q2は全モデルで出力500〜650トークンと長く、応答時間も長かった。
  - 同じモデル・質問でも run ごとに応答時間が数倍変動（3.5-flash-lite Q1: 1.07〜6.43秒、3.5-flash Q1: 4.02〜13.33秒）した。共有基盤の混雑の影響が大きく、1回の計測で性能を語るのは危険だと分かった。
  - 無料枠のレート制限について：今回は3秒スリープを挟んだ27リクエストで429は出なかったが、503（容量側の問題）は発生した。無料枠では RPM 上限だけでなく需要スパイク時の可用性自体が不安定になるため、実用アプリではリトライ＋指数バックオフとフォールバックモデルの用意が必須だと感じた。エージェントのように1質問で複数回呼ぶ設計だと、この不安定さが成功率に直接効いてくる。
