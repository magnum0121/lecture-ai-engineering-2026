## 宿題

- 取り組んだレベル：基礎
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：`app/config.py` の `RAG_TOP_K` を `5` → `2` に変更（1か所のみ）。通常のベクトル検索モードで同じ質問を `--trace` 付きで再実行した。索引の再作成は不要。
- 比較した質問と、固定した条件（モデル・対象資料など）：質問は演習と同一（`第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？`）。モデル gemini-3.5-flash-lite、対象資料 第1〜3回本講義214ページ、同梱の index.sqlite3、ツール・指示文は変更なし。
- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：
  - 変更前（RAG_TOP_K=5）：`search_materials({'query': 'LoRA QLoRA 固定 学習'})` 1回 → p.52, p.51 + 無関係な3ページ（p.60, p.47, p.61）。回答は正答・根拠 p.51, p.52。[time] 10.25秒 / 入力3,265・出力195 tokens / 応答2回 / $0.001467。
  - 変更後（RAG_TOP_K=2）：同じ引数・同じ1回呼び出し → 返るのは p.52, p.51 のみ。回答は同じく正答・根拠 p.51, p.52 で内容に劣化なし（A・B行列・4bit圧縮まで言及）。[time] 3.23秒 / 入力1,978・出力231 tokens / 応答2回 / $0.001171。
  - 差分：入力トークンが約40%削減（3,265→1,978）、費用も約20%低下（$0.001467→$0.001171）。ツール呼び出し回数・引数・回答の正しさは不変。
- 改善した例と、残る失敗・制約：改善=この質問では上位2件が必要十分な根拠（p.52, p.51）だったため、不要ページ3件分の本文をモデルに渡さずに済み、トークンと費用を削れた。残る制約=複数ページに根拠が分散する質問（例：p.13, 39, 40が必要な比較質問）ではTOP_K=2では根拠を取りこぼし、「確認できない」と答えるか部分的な回答になるリスクがある。検索語の品質が下位順位を救う保険としてのKなので、用途の質問タイプに応じて調整が必要。
- 気づき・疑問：RAG_TOP_Kは「返す件数」という単純な設定だが、そのまま入力トークン数→費用に効くことが分かりやすく観察できた。`app.retrieval` で事前にランキングを見てからKを決める運用が有効そう。一方で埋め込み検索の順位は質問依存なので、「この質問では2件で足りた」を一般化はできない。距離（類似度スコア）に閾値を設けて動的に件数を変える方式との比較も試したい。
